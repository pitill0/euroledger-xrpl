# Alertmanager Routing

EuroLedger XRPL uses Alertmanager to receive, group, deduplicate, route and silence alerts generated by Prometheus.

This block adds Alertmanager infrastructure and severity-based routing. It intentionally does not deliver notifications to an external channel yet.

## Components

- Prometheus evaluates alerting rules.
- Prometheus sends firing and resolved alerts to Alertmanager.
- Alertmanager groups alerts by alert name, component and severity.
- Critical and warning alerts use separate routing branches.
- Grafana is provisioned with Alertmanager as a datasource.
- Alertmanager state is stored in a persistent Compose volume.

## Routing

The root route uses:

```text
default-sink
```

Critical alerts use:

```text
critical-sink
```

Warning alerts use:

```text
warning-sink
```

The sink receivers do not send notifications externally. They allow the routing tree, grouping, silences and resolved alert lifecycle to be validated before selecting a delivery channel.

## Grouping

Alerts are grouped by:

```text
alertname
component
severity
```

Default timing:

```text
group_wait: 30s
group_interval: 5m
repeat_interval: 4h
```

Critical timing:

```text
group_wait: 10s
repeat_interval: 1h
```

## Inhibition

A critical alert inhibits a warning alert for the same component.

This reduces duplicate noise when a component already has a more severe active alert.

## Access

Alertmanager UI:

```text
http://localhost:9093
```

Grafana Alerting:

```text
http://localhost:3000/alerting
```

Prometheus alerts:

```text
http://localhost:9090/alerts
```

## Validation

Validate the Alertmanager configuration:

```bash
docker compose run --rm --no-deps \
  --entrypoint /bin/amtool \
  alertmanager \
  check-config /etc/alertmanager/alertmanager.yml
```

Validate Prometheus:

```bash
docker compose run --rm --no-deps \
  --entrypoint /bin/promtool \
  prometheus \
  check config /etc/prometheus/prometheus.yml
```

## Useful Commands

Inspect Alertmanager logs:

```bash
docker compose logs -f alertmanager
```

Inspect Alertmanager readiness:

```bash
curl -s http://localhost:9093/-/ready
```

List active alerts through the API:

```bash
curl -s http://localhost:9093/api/v2/alerts \
  | python -m json.tool
```

Inspect Alertmanager status:

```bash
curl -s http://localhost:9093/api/v2/status \
  | python -m json.tool
```

Reload Alertmanager configuration:

```bash
curl -X POST http://localhost:9093/-/reload
```

## Manual Verification

Stop the backend:

```bash
docker compose stop backend
```

Wait until `EuroLedgerBackendDown` fires, then inspect:

```text
http://localhost:9093
```

Start the backend again:

```bash
docker compose start backend
```

The alert should eventually become resolved and disappear from the active alert list.

## Silences

Silences can be created in the Alertmanager UI.

Use labels such as:

```text
alertname
component
severity
```

Silences are persisted in the `alertmanager_data` Compose volume.

## External Delivery

External notification delivery is intentionally deferred.

A later block can replace the sink receivers with one or more of:

- generic webhook;
- email;
- Slack;
- Telegram;
- Microsoft Teams;
- PagerDuty.

The current routing tree can remain unchanged when a delivery integration is added.
